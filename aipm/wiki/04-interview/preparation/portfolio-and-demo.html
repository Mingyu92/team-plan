AI PM 作品集与 Demo 准备

AI PM 作品集的价值不是展示“我会调用模型”，而是让面试官看到你如何把一个问题变成可验证的产品：范围怎么定、方案为什么成立、效果如何评估、成本是否算过、风险怎么兜底、现场演示失败时还能不能讲清楚。

事实：评测指南要求围绕真实任务定义成功标准并持续回归；Vibe Coding 更适合验证原型假设，涉及真实用户、真实数据和稳定服务时仍需要工程化的安全、权限、监控和交接。

建议：作品集按“问题—决策—证据—边界”组织，Demo 是证据的一部分，不是全部。

一、统一展示结构：从问题到证据

无论做 RAG、Agent 还是 Vibe Coding 项目，都可以用下面的主结构：

  1. 问题与用户：谁在什么场景下遇到什么任务困难；
  2. 目标与范围：要验证或改变什么，不做什么；
  3. 方案与关键决策：为什么选 RAG/Agent/规则/人工组合；
  4. 用户流程与 Demo：正常路径、失败路径、确认和兜底；
  5. 评测与结果：评测集、rubric、基线、线上反馈和限制；
  6. 成本与运行：单位任务成本、延迟、权限、日志和上线方式；
  7. 复盘与下一步：失败 Badcase、取舍、尚未解决的问题。

一页作品集可以只展示结论，详情页再展开证据。每个图表都写清数据口径和时间，所有未经授权的真实数据都做脱敏或改成不可识别的相对结果。

二、三类项目的展示重点

项目类型 面试官重点看什么 必须展示的证据
RAG 知识是否找对、答案是否有依据、知识库如何更新 文档来源、切片/检索流程、引用展示、分环节评测集
Agent 任务是否真的完成、工具是否受控、失败和副作用如何处理 任务卡、工具权限、状态机、轨迹、确认和回滚
Vibe Coding PM 是否能快速验证假设、是否知道原型边界 需求拆解、迭代记录、可运行路径、边界输入、已知问题和交接清单

不要把三类项目混成同一套“接入模型”的故事。RAG 的关键风险多在数据覆盖、检索和依据；Agent 的关键风险多在自主规划、工具和副作用；Vibe Coding 的关键价值是验证方向，关键风险是把原型误当生产系统。

三、RAG 项目怎么展示

1. 先讲知识问题

说明原流程为什么需要知识库：知识是否私有、更新是否频繁、是否要求可引用、人工查找或规则维护有什么瓶颈。再说明不适用的场景，例如无法提供可靠来源、需要实时交易状态但没有授权接口的任务。

2. 展示检索到回答的链路

用户问题 → 查询改写/过滤 → 文档切片与检索 → 重排/引用
        → 模型基于依据生成 → 引用展示/无法回答时兜底

作品集中至少展示一次“找对”和一次“找错/找不到”的例子：为什么召回了这段内容、答案是否被内容支持、找不到时是否老实拒答或转人工。不要只截一张漂亮答案图。

3. 准备 RAG 评测集

评测集应覆盖：高频正常问题、文档表达不同但语义相同的问题、需要多段材料的问题、知识缺失/过期问题、歧义问题和恶意/越权问题。评分可以拆为：

  • 检索：目标文档是否被召回、排序是否足够靠前；
  • 生成：答案是否正确、完整、与依据一致；
  • 产品：是否展示来源、用户能否判断可信度、找不到时是否有合理出口。

具体方法可参考从零建设评测集和如何评估 RAG 知识库的准确率?。

四、Agent 项目怎么展示

1. 先展示任务卡和工具地图

用一张图说明：用户目标、允许的子任务、只读资源、可写工具、禁止动作、完成证据和人工接管点。工具列表不要只写“支持搜索和执行”，要说明每个工具的权限和副作用。

2. 用一条轨迹讲清 Agent 如何工作

目标 → 计划 → 工具调用 → 观察结果 → 校验/重试
                           ↓
                    完成 / 确认 / 转人工 / 失败

演示时主动说明：

  • 哪些步骤由模型动态决定，哪些由代码或 Workflow 固定；
  • 工具失败时如何分类和退出；
  • 哪些动作只能生成草稿，哪些动作需要用户明确确认；
  • 每项任务的成本、延迟和最大循环在哪里限制；
  • 如何通过日志和评测集证明不是“刚好跑通了一次”。

3. 准备 Agent 轨迹评测

除了任务最终成功率，还要准备必要步骤完成率、工具业务成功率、重试率、错误归因、转人工率、风险动作拦截和成本/延迟分布。相关方法见Agent 评测与可观测性。

五、Vibe Coding 项目怎么展示

Vibe Coding 项目最适合展示“从一句话需求到可验证原型”的过程，不适合假装自己交付了一个有完整 SLA 的生产系统。建议展示：

  1. 原始问题和验证假设；
  2. 如何拆成 3-6 个可独立验证的迭代步骤；
  3. 关键提示、交互取舍和每轮验证结果；
  4. 空状态、加载、错误、空输入、超长输入和重复提交等边界；
  5. 使用了什么脱敏/虚构数据，哪些接口只是 Mock；
  6. 已知问题、未做能力、真实生产还需要哪些工程工作。

演示时不要把“能在本地跑”说成“可以直接上线”。从一句话需求到能跑的原型中的原型边界、数据安全、版本和工程交接清单可以直接用来准备追问。

六、评测集：作品集里最容易缺的一页

作品集不一定要公开全部数据，但应展示评测设计：

维度 要展示什么
来源 真实日志脱敏、专家构造、线上 Badcase、边界/对抗用例
覆盖 正常、长尾、缺失数据、多轮、工具失败和安全场景
评分 客观规则、人工 rubric、模型辅助评分和人工校准如何组合
版本 用例、标注、Prompt、模型、工具和评分器如何关联
结果 总体分数、关键分群、硬性失败和典型 Badcase
回流 新问题如何进入评测集，修复如何回归和灰度验证

如果没有足够真实数据，明确写“这是小规模探索评测”并说明不能代表线上效果。评测集的目的不是制造一个好看的分数，而是让面试官相信你知道什么被证明了、什么还没被证明。

七、成本测算：从“调用了 API”讲到“完成一项任务”

准备一个可替换参数的成本表，不要在作品集里编造价格或规模：

月度可变成本
= 有效用户数 × 人均任务数 × 每项任务调用数
  × (平均输入 token × 输入单价 + 平均输出 token × 输出单价)
  + 工具/检索/存储/浏览器执行成本
  + 人工确认与接管成本

还要报告：

  • 单次调用成本与单项有效任务成本；
  • 重试和长轨迹对成本的放大；
  • 缓存、模型路由、上下文瘦身和异步批处理的降本假设；
  • 成本上限、告警、降级和停止自主执行的条件；
  • 价格和模型版本的核验日期，动态价格以官方定价页为准。

成本估算方法见AI 产品成本测算入门和模型选型决策框架。面试中比“每月多少钱”更重要的是：你知道每个参数从哪里来，结果对哪些假设敏感，以及成本上涨时先牺牲什么、保住什么。

八、Demo 风险与备用路径

现场 Demo 的最大风险不是页面不好看，而是演示结果无法复现、无法解释或暴露安全问题。

风险 现场表现 备用路径
网络/API 不可用 加载不结束、限流、服务错误 准备离线夹具/本地数据；明确标记为回放，不冒充实时结果
输出随机或模型升级 同一输入结果不同，关键步骤失败 使用固定评测输入；预先跑过多次；准备截图和轨迹证据
外部工具失败 搜索、数据库、浏览器或登录失效 演示只读模拟工具；说明真实工具的权限和失败出口
敏感数据 屏幕、日志或 Prompt 暴露真实信息 使用脱敏/虚构数据；演示前清理环境和浏览器会话
Agent 误操作 发送、删除、付款或公开发布 关闭真实副作用；使用 dry-run；展示确认卡和回滚路径
演示路径太长 现场等待或中途迷路 把关键证据拆成短流程；准备从任意步骤继续讲解

备用路径不是把失败藏起来。正确做法是说明“实时链路此刻不可用”，切换到可验证的离线证据，并继续讲清系统真实边界。

九、面试讲解顺序：先价值，后技术，最后边界

推荐采用下面的顺序，控制每一层的细节深度：

  1. 一句话：用户、任务、AI 能力、结果；
  2. 问题：原流程为什么不够，为什么值得做；
  3. Demo：走一条最短正常路径，明确用户看到了什么；
  4. 方案：只解释和当前问题有关的 RAG/Agent/工具/数据链路；
  5. 证据：评测集、基线、线上反馈、成本和延迟；
  6. 取舍：一个最关键的选择和被放弃的方案；
  7. 边界：失败、权限、安全、数据和不能承诺的效果；
  8. 下一步：如果继续投入，优先补什么，如何验证。

如果面试官追问技术，再展开架构；如果追问业务，回到任务完成和用户价值。不要用大量术语掩盖没有评测、没有成本或没有权限边界的问题。

十、作品集与 Demo 自查清单

  • [ ] 每个项目都能在一页内讲清问题、用户、目标、范围和结果。
  • [ ] RAG 项目展示了知识来源、检索/引用和找不到时的兜底。
  • [ ] Agent 项目展示了任务边界、工具权限、状态、完成证据和人工确认。
  • [ ] Vibe Coding 项目展示了验证假设、迭代过程和生产边界。
  • [ ] 每个项目都有评测集或至少有清楚的评测计划、rubric 和限制说明。
  • [ ] 成本按单位有效任务测算，参数、价格核验日期和降级方案可解释。
  • [ ] Demo 有离线/截图/轨迹等备用证据，且不会接触真实敏感数据或副作用工具。
  • [ ] 讲解顺序遵循问题—方案—证据—取舍—边界，不把 Demo 当成全部证明。
