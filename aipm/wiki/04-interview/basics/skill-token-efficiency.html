如何设计 Skill 来降低 token 消耗?

难度:⭐⭐ 常规 出现频率:中高,成本敏感团队与 Coding Agent 岗常见

考察点

  • 是否理解 Skill「渐进披露」本身就是省 token 的主杠杆
  • 能否从 description、正文、附件分层给出可执行设计准则
  • 是否会把「省 token」和「效果变差」放在一起权衡

参考答案

一句话:省 token 的核心不是少写字,而是少加载——让无关 Skill 永远只占一行描述,相关 Skill 也只打开当前步骤需要的章节。

设计杠杆(从便宜到贵)

层级 做法 省在哪里
发现层 description 短、触发词靠前、写清「何时不用」 启动时只加载清单,列表再长也相对可控
激活层 SKILL.md 正文只放主路径;细节放 references/ 匹配后不必一次读完百科
执行层 确定性步骤用脚本,少让模型「用生成模拟计算」 少产出中间废话 token
编排层 路由/分类器决定启用哪个 Skill,禁止默认全开 避免多本手册同时进窗
运行层 限制并发 Skill 数、对长 reference 做摘要后再喂 防止单次任务上下文爆炸

PM 可写进规范的几条硬规则

  1. description 是第一成本阀:写糊了会误触发,等于把整本手册白烧进上下文。
  2. 正文控制篇幅:主路径 + 禁区 + 2–3 个例子通常够用;表格优于长散文。
  3. 大资料外置:政策全文、API 手册放 reference,并在正文写「需要时再打开某某文件」。
  4. 能脚本就脚本:排序、校验、填模板别让模型逐步「演」。
  5. 度量:看「平均每次任务加载了几个 Skill / 多少 token」,而不只看模型单价。

权衡:过度压缩会导致触发不准或步骤缺失。正确姿势是先保证触发与主路径正确,再砍冗余,并用评测集锁住效果。

追问延伸

  • 追问 1:"Skill 很多时,description 列表本身也很贵怎么办?" → 分层目录/检索式发现,或对 description 再做压缩/分桶;产品上限制「默认可见 Skill 集合」。
  • 追问 2:"为了省 token,把安全红线也做成按需 Skill,行不行?" → 不行。安全与合规红线应放 Rules/全局约束,不能赌「这次没触发」。
  • 追问 3:"和提示词缓存(前缀缓存)什么关系?" → 稳定前缀(系统提示、常用 Skill 描述)更容易命中缓存;频繁改 description 会破坏缓存命中。省 token = 少加载 + 提高可缓存前缀稳定性。
