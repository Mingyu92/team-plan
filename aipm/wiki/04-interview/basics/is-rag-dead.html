你怎么看「RAG 已死」这说法?

难度:⭐⭐ 常规 出现频率:高,RAG/检索/Agent 相关面试常被拿来"接地气"地问一下

考察点

  • 是否只会背"RAG 没死"的结论,还能不能讲清楚"死的是什么、活的是什么"
  • 能否区分"检索"这个目标和"向量检索"这一种具体实现手段
  • 能否落到场景分流,而不是空喊"RAG 永不为奴"

参考答案

一句话:死的是 2023 年那套"固定切块 → 固定 Top-K → 固定拼 Prompt"的 Naive RAG 流水线,不是"先找证据、再基于证据回答"这个思路本身。

为什么会显得"死了"

社交媒体上"RAG 已死"的论据通常是两条:上下文窗口都到百万级了,还检索个啥;Coding Agent 用 grep 就能读懂整个仓库,不需要向量库。这两条冲击的其实都是同一个默认设定——"检索=向量检索,且是系统提前写死的固定步骤",不是"检索"这件事本身。Naive RAG 的三个死穴才是真正被吐槽的对象:

  1. 固定切块:不管文档结构机械切块,容易把语义单元切断
  2. 固定 Top-K:不管问题难度和知识库规模都取固定数量候选
  3. 无任务意识:检索在生成之前就写死跑完,模型没机会判断"该不该查、查哪里、查一次够不够"

RAG 思想没消失,演进出三条路

阶段 检索怎么做 谁决定检索策略
Naive RAG 固定切块 → 固定 Top-K 向量检索 系统提前写死
Hybrid RAG 向量 + BM25 等多路召回,再融合/重排 系统按配置好的规则
Agentic Retrieval 模型先判断查询类型,再选检索粒度、决定是否多轮补查 模型按任务动态决定
Agent + Tools 检索降级为众多工具之一,和 grep、API 并列由模型统一规划 模型自主规划

到了最后一阶段,"RAG"这个词反而不太被单独提起,不是因为它消失了,而是融入了更大的"上下文工程"体系。

场景分流,不是非黑即白

场景特征 更适合
FAQ、客服知识库、制度问答(问题形态稳定、单跳可答) 传统 / Hybrid RAG 就够,延迟低、成本可控、行为可预测
需要精确命中工单号、型号等专有名词 Hybrid RAG(向量 + BM25),不必上 Agent
多步骤代码排障、跨文件定位 Agent(检索作为工具之一),需要"查一次看结果再决定下一步"
问题类型混杂、难以预判 Agentic Retrieval,让模型自己先判断再选路径

面试加分句:判断该不该"升级"看任务是否有内在分支(有时候查一次不够,有时候根本不用查),不是看这个词最近热不热。

追问延伸

  • 追问 1:"长上下文这么大了,为什么还要 RAG?" → 窗口大小决定"能塞多少",不决定"该不该塞"。还要核对成本随库规模的增长曲线、多用户并发共享、精确引用来源、多租户权限过滤这几个维度,详见《长上下文 vs RAG》的决策树。
  • 追问 2:"Coding Agent 用 grep 不用向量库,是不是说明向量检索没用了?" → 是场景权衡,不是取代。代码仓库结构清晰、可用符号/文件名精确定位,grep 天然合适;企业文档知识库缺乏这种结构,语义检索依然是主力手段。
  • 追问 3:"如果团队现在还在用 Naive RAG,你会先升级哪一步?" → 优先补齐 Hybrid 检索(关键词 + 重排),这一步性价比通常最高;再评估是否真的需要上 Agentic 检索,不要一步跳到最复杂的方案。
