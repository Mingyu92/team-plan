RAG 系统有哪几种检索路径?分别适合什么场景?

难度:⭐⭐ 常规 出现频率:高,RAG/搜索/知识库相关一面常见

考察点

  • 能否说出不止「向量检索」一种路径
  • 是否理解多路召回 + 融合/重排的产品动机
  • 能否按查询类型做路径选型,而不是堆技术名词

参考答案

一句话:生产级 RAG 很少只靠一种检索——通常是多路召回(覆盖)再融合/重排(精度)。

常见检索路径

路径 在找什么 更适合 典型弱点
向量语义检索 「意思相近」 改写问法、同义表达、模糊需求 专有名词、精确编号易飘
关键词 / 全文检索(BM25 等) 「字面命中」 型号、工单号、法条编号、人名 同义改写、语义跳跃差
结构化过滤 元数据条件 时间、权限、租户、类目、状态 不会理解自然语言本身
知识图谱 / 关系检索 实体关系 「A 的上级是谁」「部件属于哪」 建图成本高,覆盖不全则空
SQL / OLAP 查询 表格事实 指标、订单、库存等可计算问题 需 Text-to-SQL 与权限治理
网页/工具实时检索 新鲜外部信息 新闻、股价、政策更新 噪音大、要引用与可信度策略
会话/点击反馈检索 个性化或难例 追问、相关推荐、badcase 库 冷启动与隐私约束

产品上怎么组合

  1. 路由:先判断查询类型(精确 ID / 语义问答 / 看数 / 要新闻),再开对应路径。
  2. 并行召回:语义 + 关键词是最常见底盘;有权限/类目则先过滤。
  3. 融合与重排:统一候选池后再 Rerank 或规则加权。
  4. 生成前裁剪:只保留 Top-K 证据,并尽量带来源。

面试加分句:路径选择是产品决策——考的是「用户问题形态」,不是「向量数据库品牌」。

追问延伸

  • 追问 1:"只有向量检索够不够?" → 对 FAQ/文档语义问答常常起步够用;一旦出现编号/专名/权限/看数,就会不够,要补关键词或结构化路径。
  • 追问 2:"多路召回变慢变贵怎么办?" → 路由减路、缓存热问、异步预取、对简单查询走短路径;用延迟与成本预算做开关。
  • 追问 3:"如何验收多路是否有用?" → 按 query 分桶看召回命中与最终答案正确率;证明「加一路」带来的增益大于延迟/成本。
