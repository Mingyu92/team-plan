Badcase 分析方法论:收集、归因、分发、验证

为什么 Badcase 分析是 AI PM 的日常功课

评测集和 LLM 评分体系(见《从零建设评测集》、《主观任务怎么评》)解决的是"如何系统性地衡量效果",但再完善的评测集也无法覆盖线上所有真实场景。真正驱动产品持续变好的,是一套稳定运转的 badcase 闭环:发现问题 → 搞清楚问题出在哪一环 → 分给能修的人 → 修完验证是否真的解决,并且不引入新问题。这件事本身没有太多"高深算法",却是 AI 产品经理最核心的日常工作之一——因为归因和分发,恰恰是最需要产品视角的环节。

Badcase 从哪里收集

Anthropic 工程团队在讨论 Agent 评估时给出的建议同样适用于所有 AI 产品:不要等一套"完美的评测体系"才开始,先把手头已有的问题线索转化成 badcase。常见的收集渠道:

渠道 具体形式 特点
用户反馈 点赞/点踩、"回答有误"举报入口、客服工单、社群吐槽 直接反映真实体验,但样本量取决于反馈意愿,存在"沉默的大多数"
人工抽检 按比例随机抽样线上对话,由业务/QA 团队人工复核 能发现用户不会主动反馈的问题(如态度生硬但不算"错")
生产监控 异常指标告警(如响应超时、拒答率突增、置信度骤降)、日志关键词扫描 能及时发现系统性问题,但需要提前埋点和设阈值
Bug 追踪与支持队列 已有的 Bug 系统、客户成功团队上报的问题 现成渠道,复用已有工作流,门槛低

Anthropic 的建议是把这些渠道产出的问题"按用户影响程度优先排序",而不是眉毛胡子一把抓——一个每天被上千用户触发的 badcase,和一个只出现过一次的极端边界情况,处理优先级完全不同。

归因分类树:问题到底出在哪一环

收集到 badcase 之后,最容易犯的错误是"发现不对就找算法同学",但很多时候问题根本不在模型本身。一个实用的归因分类树,把常见问题归为五大类:

Badcase 出现
   │
   ├─ 检索问题(适用于 RAG/知识库类产品)
   │    ├─ 该召回的文档没召回(召回率不足/切片策略问题)
   │    ├─ 召回了但排序靠后(重排问题)
   │    └─ 知识库本身缺这块内容(内容覆盖盲区)
   │
   ├─ 模型问题
   │    ├─ 模型能力不足(推理/计算/长文本处理超出能力边界)
   │    ├─ 模型幻觉(编造检索材料中不存在的信息)
   │    └─ 模型没有遵循指令(忽略了 Prompt 中的约束)
   │
   ├─ Prompt 问题
   │    ├─ 指令本身有歧义,模型理解方向没错但结果不是产品想要的
   │    ├─ 缺少必要的示例/上下文,模型"猜"错了格式或语气
   │    └─ Prompt 版本更新后引入回归(新问题在老 Prompt 下不存在)
   │
   ├─ 数据问题
   │    ├─ 训练/微调数据分布与真实场景不符
   │    ├─ 知识库内容过时或存在错误
   │    └─ 标注质量问题(评测集本身标错了标准答案)
   │
   └─ 预期问题(不是"错",是"没达到用户期待")
        ├─ 用户对产品能力边界有误解(该场景本来就不支持)
        └─ 产品没有提前设定合理预期(如没有说明"仅供参考")

这棵树的价值在于:同一个"看起来像模型答错了"的现象,归因路径可能完全不同。比如用户反馈"机器人不知道我们公司最新的退货政策"——可能是知识库没更新(数据问题),可能是切片时把政策条款切断了(检索问题),也可能是模型看到了正确材料但没引用好(模型问题)。不先分环节排查,直接让算法同学"优化一下模型",大概率是无效劳动。

RAG 类产品的排查思路可以进一步参考《如何评估 RAG 知识库的准确率?》中"分环节评测框架"的表格——检索、重排、生成、端到端各自独立验证,badcase 归因本质上是同一套框架的逆向应用。

如何分发到对应团队

归因清楚之后,分发要解决两个问题:谁来修、修完怎么知道修好了。

归因类别 通常对应团队 分发要点
检索问题 检索/工程团队 附上具体的召回结果截图,标明"应该召回但没召回"的目标文档
模型问题 算法团队 附上完整对话上下文 + 复现步骤,标注是能力不足还是指令遵循问题
Prompt 问题 PM/Prompt 负责人自己 通常不需要"分发"——这是 PM 的直接责任田
数据问题 知识库运营/数据团队 指出具体过时/错误的内容条目,给出修正建议
预期问题 PM + 设计 转化为产品设计问题:补充免责说明、优化拒答话术、调整功能边界宣传

一个容易被忽视的操作细节:每条分发出去的 badcase,都要同步登记进评测集候选池(见《从零建设评测集》中"Badcase 回流"这一用例来源),否则修复效果无法在下一次迭代中被验证,只能靠"记忆"判断"好像修好了"。

修复后回归验证

Badcase 修复不是"提交了代码/改了 Prompt"就结束,而要闭环到验证:

  1. 点验证:把这条 badcase 本身重新跑一遍,确认修复生效。
  2. 面验证:把这条 badcase 加入回归测试集(而不是评测集里即用即弃),防止未来的改动让它复发。
  3. 副作用检查:在完整评测集上重新跑一次全量评测,确认修复这一个问题没有引入新的回归——这一步经常被跳过,却恰恰是"修好一个、坏了三个"的高发环节。
  4. 上线灰度观察:小流量验证真实效果,而不是只信离线评测分数。

这几步呼应了 《从零建设评测集》里"上线验收流程"的设计逻辑——badcase 修复本质上是一次微型迭代,同样需要走完整的验收闭环,不能因为"只是修一个小问题"就跳过验证。

Badcase 例会机制

比工具更重要的是机制。一个可落地的 badcase 例会设计:

要素 建议
频率 高频迭代期(如上线初期)每周一次;稳定期可两周一次
参会人 PM、算法、检索/工程、数据/知识库运营,视归因类型灵活拉人
例会输入 上周新增 badcase 列表(按归因分类树预先打好标签)、优先级排序
例会产出 每条 badcase 的归因结论、responsible owner、预计修复时间
追踪机制 维护一张滚动看板,标注"待归因/已分发/修复中/待验证/已闭环"状态
长期沉淀 定期(如每月)复盘高频归因类型,推动系统性解决(如某类检索问题反复出现,说明该做切片策略的整体优化,而不是逐条打补丁)

例会的核心价值不是"过一遍问题清单",而是逼着团队持续做"分环节归因"这件事,防止 badcase 堆积成谁都不认领的黑洞。

"模型指标涨了,业务指标没涨"怎么排查

这是面试和实际工作中都极高频的场景(参见《如何构建大模型效果评测体系?》中的追问延伸),本质上是一次特殊的"badcase"——不是某一条用例错了,而是整个评测体系与业务现实脱节了。排查思路可以按下面的顺序展开:

  1. 评测集分布是否漂移:离线评测集的用例分布,和线上真实流量分布是否一致?如果评测集还是半年前的用例,而线上已经出现大量新场景,分数再高也不能代表真实体验。
  2. 评测维度是否遗漏:是不是只看了"准确率"这一个指标,而业务体验还依赖响应速度、语气、拒答率等未被纳入评测的维度?
  3. 指标定义是否对齐:模型侧的"正确"和业务侧的"有用"是不是同一件事?比如检索召回率涨了,但用户真正在意的是"问题有没有被解决",这是两个不同的指标。
  4. 是否存在环节衰减:模型能力提升了,但上下游(比如展示层、交互设计、用户引导)没有同步跟上,好的回答没有被用户感知到。
  5. 是否是短期噪声:业务指标本身波动大、样本量不足、观测周期太短,导致"没涨"只是统计噪声而非真实效果缺失。

排查这类问题时,建议直接把它当作一条最高优先级的 badcase 走完整归因流程:先确认是评测集问题还是产品体验问题,再决定该找算法团队修模型,还是该找产品和设计重新设计交互——这正是本文归因分类树里"预期问题"和"数据问题"最容易被忽视,但在这个场景下往往是真正病灶的地方。
