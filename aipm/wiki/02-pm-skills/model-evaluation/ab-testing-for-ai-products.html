AI 产品的 A/B 测试：概率性输出下如何做实验

选题启发：磊叔《关于 AI 产品经理的 100 个问题》Q54、Q65（实验为何易误判、与传统 A/B 的差异）。正文为原创方法论，不复述 PDF 中的具体数字与轶事。

事实：大模型同一输入可产出不同输出；官方评测指南把「变异性」当作必须用 evals 与持续评估来应对的前提，而不是可忽略噪声。见文末资料。

建议：把线上 A/B 当作「业务因果」工具，把离线评测当作「输出质量」工具；二者对齐后才能解释「用户变了，是因为模型真变好了，还是因为方差/新奇效应在骗人」。

传统产品改一个按钮文案，同一用户看到的通常是固定界面；随机性主要来自「分到哪一组」。AI 产品再加一层：同一组、同一用户、同一问题，模型也可能给出不同回答。若不把这层方差写进实验设计，很容易把随机波动当成方案胜负。

本文回答两件事：AI A/B 和传统 A/B 差在哪；概率性输出下，实验该怎么重新设计。采样参数与可复现性的基础见为什么大模型的输出每次都不一样?；指标怎么分层见AI 产品指标体系。

一、传统 A/B vs AI A/B：差异表

维度 传统产品 A/B AI 产品 A/B
处理对象 界面、流程、规则等相对确定的体验 Prompt / 模型 / 检索 / Agent 策略等，输出本身是概率的
组内一致性 同组用户看到的体验大体一致 同组内也可能因采样、上下文、工具结果而差异很大
主要噪声来源 用户异质性、季节性、外生活动 上述全部 + 生成方差 + 任务难度长尾
「改动生效」的含义 用户看到了新 UI/新规则 用户接触到了新系统，但单次输出质量仍在抖动
离线证据 多为可用性走查、规则回归 需要任务级评测集 / rubric / 安全闸门（见从零建设评测集）
线上主问题 「用户行为是否因方案而变？」 同上，还要追问「行为变化是否对应质量变化，还是方差/新奇效应？」
护栏指标 崩溃率、延迟、核心漏斗 再加上拒答率、幻觉/安全事件、转人工、单位任务成本等
可复现性 回放同一 UI 即可对照 需固定模型版本与采样设置，或接受「分布可比」而非「逐字可比」

一句话：传统 A/B 比较的是两种确定体验；AI A/B 比较的是两种随机过程。 结论要建立在「分布差异」上，而不是「某几次好看的回答」上。

二、为什么容易得出错误结论

1. 生成方差被当成方案差异

OpenAI 官方写得很直接：生成式 AI 具有变异性，同一输入也可能得到不同输出，传统软件测试方法不够用，需要用结构化 evals 来度量表现。把这一点搬到线上：若只看短窗口、小样本，或只看个别会话截图，B 组「看起来更好」完全可能是运气。

可操作含义：用户级指标（转化、完成率）要按用户/会话聚合后再比组；不要拿「某一条生成答案」当实验单元去宣称胜负。

2. 样本量与功效仍按「确定性体验」估算

在线对照实验的经典要求仍然成立：先定假设与总体评估准则（OEC），再按最小可检测效应（MDE）、方差、显著性水平与功效估算样本量；过早 peeking、多重比较会抬高假阳性。Kohavi 等人的在线实验实践反复强调：拿到数字不难，拿到可信数字很难。

AI 场景通常还会抬高方差（开放域生成、任务难度不均、重试与转人工）。因此：

  • 用历史流量先估真实方差，再算样本量，而不是套用别的团队的「大概要跑几天」；
  • 若方差明显高于历史 UI 实验，应预期需要更长窗口或更大流量——具体倍数取决于你的指标与流量，不是行业统一红线。

3. 新奇效应与学习效应

引入「会说话的新能力」时，用户常会多点几下、多试几次（新奇效应），或因不熟悉而暂时变慢（首因/学习效应）。Kohavi 等对受控实验中的 puzzling outcomes 指出：新奇与首因方向相反，短期 lift 可能夸大或掩盖长期价值；可疑时应延长实验、按曝光天数看趋势，或重点看新用户（较少受旧习惯干扰）。

可操作含义：AI 功能上线实验不要只看前两天的「新鲜劲」；同时观察护栏（点踩、转人工、成本）是否在衰减期后仍可接受。

4. 线上涨了、离线没涨（或反过来）

这是 AI 特有的解释陷阱：

现象 常见解释方向
离线评测升、业务不动 评测集与线上分布不一致；入口/展示/信任问题；延迟或成本拖垮体验
业务升、离线不动或不降 新奇效应；外生活动；用户「多聊」被误当成成功；评测维度没覆盖真实价值
两边都动但方向相反 指标定义冲突（例如更长回答抬高满意度却抬高成本、降低一次解决率）

指标冲突如何排序，见AI 产品指标体系；badcase 与「模型分涨、业务不涨」排查见Badcase 分析方法论。

三、把实验拆成两层：离线质量门 + 线上因果门

Anthropic 将 A/B 测试列为对照基线/旧版本的定量方法之一，同时强调成功标准要具体、可测。OpenAI 面向业务落地的论述也指出：对外产品，evals 不能替代传统 A/B 与产品实验，二者应互补——evals 看清系统在任务上的表现，实验看清真实用户与业务结果。

推荐默认链路：

假设：改 Prompt/模型/检索 → 某类任务质量提升 → 用户完成率/采纳率提升 → 业务结果改善
        │                         │                      │
   离线评测集 + 护栏          灰度/小流量观察质量与稳定性    正式 A/B（用户随机）
  1. 离线：在固定评测集上比较版本；主观任务用 rubric / LLM-as-a-Judge 并做人工校准（见主观任务怎么评）。
  2. 灰度：小流量看延迟、错误、安全、成本是否可接受。
  3. 线上 A/B：用户随机分流，主看预注册的业务/行为 OEC，护栏指标一票否决。
  4. 对齐解释：线上显著时，回看离线分维度是否同向；不同向就先查分布漂移与指标定义，而不是直接全量。

四、可操作的实验设计原则（至少做到这些）

原则 1：预注册假设、OEC、护栏与停止规则

上线实验前写清：

  • 假设：改的是什么（模型版本、Prompt、检索、工具策略），预期改善哪类任务；
  • OEC：一个（或极少几个）主指标，定义分子分母与触发人群（只统计真正曝光到 AI 能力的用户）；
  • 护栏：安全事件、严重幻觉、延迟分位、单位任务成本、转人工率等；
  • 停止规则：计划样本量/时长、是否允许提前终止、如何处理多重比较。

未预注册就「看着涨了就推全」——在方差更大的 AI 场景里，假阳性成本更高。

原则 2：显式处理生成随机性，而不是假装不存在

按场景选策略（可组合）：

策略 适用 注意
固定模型版本 + 记录采样参数 所有对照实验 版本漂移会污染结论
降低 Temperature / 约束解码（若产品允许） 客服、抽取、强一致场景 可能牺牲多样性；见输出随机性面试题
离线同一用例多跑，报告均值与波动 版本准入 单次跑分不够；Agent 场景尤甚
线上以用户/会话为分析单元 业务 A/B 避免把单次 token 抽样当独立样本滥用

目标不是「消灭随机」，而是让两组面对可比的随机过程，并把剩余方差算进功效。

原则 3：离线与线上必须互相校验

  • 上线前：离线未过安全/质量闸门，不进入正式 A/B；
  • 上线中：抽样线上日志回灌评测集（脱敏），检查分布是否漂移；
  • 上线后：若 OEC 显著，抽检会话与 badcase，确认机制故事成立；若不显著但离线大涨，优先查「评测是否过拟合」和「体验是否触达」。

OpenAI 的评价实践强调：围绕真实任务定义成功标准、持续评估、用生产日志扩充用例——这与「只跑一次 A/B 就宣布模型胜利」是对立的。

原则 4：为新奇效应与长尾任务留观察窗口

  • 按曝光后天数看 lift 是否衰减；衰减后仍为正，才更像真实价值；
  • 分群：新用户 / 老用户、任务类型、租户、模型层级；
  • 高风险或低频高损任务：不要只用总平均 OEC，设置独立护栏或单独实验切片。

「要跑几天」没有普适答案：由功效计算、业务周期（工作日/活动）和新奇衰减是否结束共同决定。把「别人说的 N 天」当成标准，本身就是实验设计失败。

原则 5：实验结论要能落到产品动作

胜出方案全量时，同步准备：

  • 回滚开关与流量配比；
  • 反馈与兜底是否跟上（见兜底、反馈与预期管理）；
  • 新 badcase 回流评测集，避免下一轮实验建立在过时金标上。

A/B 不是终点，是迭代闭环里的一环。

五、PM 实验评审清单

  • [ ] 假设写清「改动 → 质量机制 → 用户行为 → 业务结果」，且 OEC 与护栏已预注册。
  • [ ] 离线评测集覆盖本次改动的任务类型，安全项有一票否决。
  • [ ] 模型/Prompt/检索版本与采样参数已固定并可追溯。
  • [ ] 样本量基于历史方差与 MDE，而不是套用外部「经验天数/倍数」。
  • [ ] 分析单元是用户或会话；触发规则只统计真实曝光。
  • [ ] 已计划检查新奇/学习效应（趋势、新老用户、曝光天数）。
  • [ ] 线上结论与离线分维度结果有对照解释；冲突时有排查路径。
  • [ ] 全量方案附带回滚、反馈入口与评测集更新责任人。
