RAG 没死:死的是 Naive 固定流水线

2026 年这一年,社交媒体上时不时会冒出"RAG 已经死了"的论调,理由通常是"上下文窗口都到 1M 了,还检索个啥"或者"Coding Agent 用 grep 就能读懂整个仓库,不需要向量库"。这类标题足够抓眼球,但把"RAG"和"向量检索"划了等号,又把"检索"和"死"划了等号,两步都站不住。更贴近实情的判断是:过时的是 2023 年那套"固定切块 → 固定 Top-K → 固定拼上下文"的入门版流水线,检索这件事本身从未退场,只是换了个更聪明的组织方式。

一句话说清

RAG(检索增强生成)的核心动作从来只有一件事:先找到相关材料,再让模型基于材料生成答案。至于"怎么找"——向量语义检索只是其中一种手段,BM25 关键词匹配、结构化过滤、SQL/API 查询、文件系统搜索,都是合法的检索路径。真正发生变化的,是"找"这个动作从"系统提前写死的固定步骤"变成了"模型按任务动态决定"。

RAG 不等于向量检索

把 RAG 等同于"向量数据库 + Embedding"是最常见的误解。生产级系统里,检索路径通常是多种手段的组合:

检索路径 适合找什么 典型弱点
向量语义检索 改写问法、模糊需求、同义表达 专有名词、精确编号容易漂
BM25 / 关键词检索 型号、工单号、报错代码等字面命中 语义跳跃、同义改写差
结构化过滤 / SQL 时间、权限、指标、库存等可计算问题 需要 Text-to-SQL 与权限治理
文件系统 / 代码检索(grep 类) 已知文件结构、代码符号、目录明确的仓库 无结构、跨文件的语义关联弱
API / 工具实时查询 新闻、股价、政策等新鲜外部信息 依赖工具可用性与调用成本

完整的路径对照与融合策略见面试题《RAG 系统有哪几种检索路径?》。这张表想说明的是:"检索"是一类目标(找到证据),不是一种具体技术,Naive RAG 之所以显得过时,恰恰是因为它把目标和其中一种实现方式焊在了一起。

死掉的是什么

2023 年前后大多数 RAG 教程都长一个样:文档切成固定大小的块,转成向量存进库,用户一提问就固定取 Top-K 块拼进 Prompt。这套"Naive RAG"有三个共同特征,也正是被诟病的地方:

  1. 固定切块:不管文档结构,机械地按字数切,容易把一个完整语义单元切断成两半,检索回来的片段可能既不完整也不必然相关。
  2. 固定 Top-K:不管问题难度和知识库规模,永远取固定数量的候选,简单问题浪费上下文,复杂问题证据不够。
  3. 无任务意识:检索这一步在生成之前就已经跑完、写死,模型自己没有机会判断"这个问题到底该不该查、该查哪里、查一次够不够"。

这三条叠在一起,导致的典型症状是:检索到的材料"看起来相关但答不对题",或者简单问题也要跑一遍完整检索链路,浪费延迟和成本。这才是社交媒体上"RAG 已死"讨论真正在吐槽的对象——是这套僵化流水线,不是检索这件事本身。

重新打开"开卷考试"这个比喻

RAG 常被比作"开卷考试":允许模型翻书作答,而不是凭记忆硬答。但这个比喻在 Naive 阶段其实只讲了一半。

  • Naive RAG 更像"盲目翻书":考试铃一响,不管题目问的是什么,先固定翻到目录第 3-7 页,把这几页抄下来贴在答题卡背面,然后才开始看题。翻页动作和题目内容无关,翻的页数也永远一样。
  • Agentic 检索更像"先判断考点再翻书":看清题目在问什么——是要背诵原文,还是要查一个具体数字,还是压根不用翻书直接能答——再决定翻哪一章、翻几次、要不要翻完一次后再翻一次确认。翻书本身没有变,变的是"翻之前先想一步"。

这个差别听起来简单,但决定了系统在遇到"检索一次不够""证据分散在多处""问题其实不需要查库"这几类场景时,是死板碰壁,还是能自己调整策略。

演进路径:从固定流水线到会用工具的 Agent

RAG 的实践从 2023 年到 2026 年大致经历了三个阶段,后一阶段不是推翻前一阶段,而是把它变成自己可调用的能力之一:

阶段 检索怎么做 谁来决定检索策略 代表实践
Naive RAG 固定切块 → 固定 Top-K 向量检索 → 拼 Prompt 系统在生成之前写死 2023 年前后的入门教程
Hybrid RAG 向量 + BM25 等多路召回,再融合/重排 系统按经验配置好的规则 Anthropic Contextual Retrieval
Agentic Retrieval 模型先判断问题类型,再选择检索粒度(整块/整文件/跨库)和是否多轮补查 模型按当前任务动态决定 LlamaIndex 的 auto_routed 检索模式
Agent + Tools 检索只是众多工具之一,模型自主规划何时查库、何时查代码、何时调 API、何时直接回答 模型统一规划,检索降级为可调用工具 Coding Agent 里检索与 grep、执行反馈并列使用

到了 Agent + Tools 阶段,"RAG"这个词本身反而不太被单独提起——不是因为它消失了,而是因为它融入了更大的系统,和查询改写、重排序、记忆机制一起被统称为"上下文工程"(context engineering)的一部分。少数派作者王树义在《RAG 过时了吗?》一文中把这个现象总结得很直接:过时的是"切块加向量加 Top-K"的入门版,RAG 的思路本身"没有消失,而是融入了更大的体系"。

场景分流:不是所有场景都要升级到 Agent

"该不该上 Agentic 检索"不是非黑即白的选型题,而是要按场景分流:

场景特征 更适合 理由
FAQ、客服知识库、制度问答 传统 / Hybrid RAG 就够 问题形态稳定、单跳即可回答,固定流水线延迟低、成本可控、行为可预测
需要精确编号/工单号命中 Hybrid RAG(向量 + BM25) 语义检索对专有名词不敏感,叠加关键词匹配即可解决,无需上 Agent
多步骤代码排障、跨文件定位 bug Agent(检索作为工具之一) 需要"查一次、看结果、判断下一步查哪"的循环,固定 Top-K 检索无法适应
问题类型混杂、难以预判(有时候查一句话就够,有时候要跨多文档综合) Agentic Retrieval 需要模型先判断查询类型再选检索策略,而不是所有问题走同一条路径
涉及看数、算指标、查库表 结构化检索 / NL2SQL,而非文本检索 答案在表格里,不在文档片段里,检索目标本身就不一样

判断标准很朴素:如果每一次提问都能用同一套固定检索规则覆盖,就没必要为了追新引入 Agent 的复杂度和不可预测性;反过来,一旦出现"有时候要查两次""有时候根本不用查"这种任务内在的分支,固定流水线迟早会露出短板。

给 AI PM 的判断框架

  1. 先问"检索目标",再问"检索技术":是要精确命中编号,还是要语义相似,还是要算一个数字?目标不同,该选的检索路径完全不同,不要把"上不上向量库"当成唯一决策点。
  2. 区分"证据获取"和"检索粒度是否该动态调整":多数知识库问答场景,证据获取用 Hybrid RAG 已经够稳;只有当任务本身有多步骤、多分支时,才需要让模型自己决定检索策略。
  3. 别让长上下文成为"不做检索"的借口:窗口变大解决的是"能塞多少",不解决"该信哪一段",两者的权衡见《长上下文 vs RAG》。
  4. 升级到 Agentic 检索前,先算清楚多出来的延迟和成本是否有对应的效果收益——参考 Anthropic Contextual Retrieval 的思路:先把混合检索和重排做扎实,这一步的性价比往往最高,再考虑是否需要模型自主决策检索策略。
