系统提示词设计与 Prompt 工程化:把玄学变工程

前两篇讲的是"怎么写好一条 Prompt"(Prompt 基本功)和"怎么让模型稳定吐出结构化数据"(结构化输出)。但一个 AI 产品线上跑的从来不是"一条 Prompt",而是一套需要长期维护、反复修改、被无数次调用的系统。这篇要解决的是更进一层的问题:Prompt 从"一次写好就行"变成"持续迭代的产品资产"之后,该怎么管理。

System Prompt 与用户输入的分层

绝大多数模型 API 都不是把"系统设定"和"用户这一句话"混在一起丢给模型,而是显式分层:

  • Anthropic 的 Messages API 里,system 是一个独立参数,和 messages 数组(用户/模型的对话轮次)是分开的。system 里放的是相对稳定、跨轮次都生效的设定——身份、语气、能力边界、输出规范。
  • OpenAI 的做法把角色分得更细:developer(开发者预设的指令)、user(终端用户的输入)、assistant(模型自己的历史回复)。官方明确指出 instructions 参数的优先级高于用户输入——也就是说,当用户在对话里试图说"忽略你之前的设定"时,开发者层的指令原则上应该继续生效,这是一种从 API 设计层面就内置的权限分级。

这套分层对 PM 的实际意义是:产品的"人格"和"边界"应该写在系统层,而不是散落在每一次的用户 Prompt 拼接逻辑里。系统层的内容变更频率低、影响面广,理应被当作正式的产品配置来管理,而不是研发同学在代码里随手拼字符串。

产品人格与边界设定

系统层通常要交代清楚三件事:

  1. 身份与语气:这是什么产品、以什么口吻说话(Prompt 基本功中"角色"要素的产品级放大版)——比如金融类助手需要严谨克制,陪伴类产品可以更活泼,这个基调不应该每次对话重新设定,而应固化在系统层。
  2. 能力边界:哪些问题该答、哪些该拒答、遇到超纲问题怎么应对(转人工、给免责声明,还是老实说"我不知道")。边界设定得越具体,产品行为越可预期——比如与其笼统写"不要给医疗建议",不如写清楚"遇到具体病症咨询,先给出通用健康信息并明确建议就医,不给出诊断结论"。
  3. 兜底话术:模型能力不够、检索不到材料、触发结构化输出失败时,该说什么——这些"失败路径"上的话术同样是产品设计的一部分,而不是留给模型随机应变。

注入风险意识(简介)

系统层的设定看似"权限更高",但并不天然安全。Anthropic 在其安全工程博客中明确提示:模型在处理外部内容(网页、用户上传的文档、图片里的文字)时,那些内容里夹带的指令有可能被模型误当成"新的指令"来执行,从而覆盖掉系统层原本设定的行为——这类风险统称为 Prompt 注入(Prompt Injection)。对于会调用工具、访问外部数据、执行浏览器/电脑操作的 Agent 类产品,这个风险尤其突出,官方系统卡里也披露过针对性红队测试的攻击成功率数据。

这里不展开攻防细节,PM 只需要建立三条基本意识:

  • 系统指令不是绝对安全的"护城河",外部输入(尤其是模型要"阅读"或"执行"的内容)需要被当作不可信数据处理,理想情况下用明确的标签/边界把"待处理的外部内容"和"应该遵循的指令"物理隔开。
  • 权限最小化:Agent 能调用的工具、能访问的数据范围,应该按实际需要收窄,而不是"先都开着方便调试"。
  • 高风险操作要有人工确认环节,不能假设系统 Prompt 里的"请谨慎操作"这类软约束能完全兜底。

Prompt 版本管理:像管代码一样管 Prompt

Prompt 改一个字都可能改变输出效果,这决定了它不能是"改完直接发布"的散装文本,而应该纳入正式的版本管理:

  • OpenAI 官方的建议是把 Prompt 存放在应用代码里而不是当作一次性文本,这样才能获得"带类型的输入、代码审查、测试用例、正常的部署流程"这些工程化好处——本质上是把 Prompt 当成代码的一部分来对待,而不是运营人员在后台随手改的配置项。
  • Anthropic 的 Console 提供了配套的工具链,建议的使用顺序是:先生成第一版草稿 → 用"模板与变量"功能把 Prompt 中固定不变的部分和每次替换的变量(如用户输入、检索到的材料)拆分开 → 再用"Prompt 改进器"迭代优化。这个改进器会自动应用一些通用技巧(比如补充链式推理提示、把示例统一转换成 XML 格式、增加前缀引导),官方给出的案例显示,这套流程能让某个多标签分类任务的准确率提升 30%。

对 PM 来说,版本管理落地到日常工作至少要做到三件事:每次修改 Prompt 都要有版本号和变更记录(改了什么、为什么改)、变量部分(用户输入等)和固定部分(系统设定、指令)要分离存放、任何一次"效果变差"都要能快速定位到是哪个版本引入的。

回归测试与评测集联动:改一个词也要跑回归

这是 Prompt 工程化里最容易被跳过、却最关键的一环:Prompt 的改动没有"看起来更合理就应该更好"这回事,任何改动都必须跑一遍评测集,才能知道它是真的变好了还是在某些场景下悄悄变差了。

大模型输出本身具有随机性,同一个 Prompt 换一批输入效果可能天差地别,这也是为什么"改一个词"也不能凭直觉判断——本仓库另一篇文章已经系统讲过评测集怎么建(从零建设评测集),这里不重复展开,只强调它和 Prompt 迭代之间的联动关系:评测集不是模型上线前才用一次的"验收工具",而应该是每次 Prompt 改动的强制回归关卡。

具体到工具层面,官方生态目前的动态值得关注:

  • OpenAI 的 Evals 能力里有一个明确的用例叫"检测 Prompt 回归"——把新旧 Prompt 版本跑在同一个存量数据集上做对比,自动标记出行为发生变化的样本供人工复核。不过需要提醒的是,OpenAI 官方已宣布其独立的 Evals 平台将于 2026 年 10 月 31 日起转为只读、11 月 30 日正式下线,相关能力和第三方评测工具(如已被 OpenAI 收购的开源项目 Promptfoo)的整合方向,是 2026 年下半年值得持续关注的变化,PM 在选型评测工具链时应留意官方渠道的最新公告,而不是依赖某个具体产品名。
  • Anthropic 的建议路径是先在"定义成功标准"文档里明确指标,再围绕指标建立评测集,Prompt 每次改动都对照这套标准跑分——这与 Anthropic Console 里"模板与变量"功能预留的评测入口是配套设计的:把变量和固定模板拆开之后,才方便对同一个模板批量灌入评测集里的用例。

落地到团队协作习惯上:任何一次 Prompt 修改(哪怕只改了一个形容词、调整了一句话的语序),都应该先在评测集上跑一遍再合并,而不是"感觉应该没问题"就直接上线——这是把 Prompt 优化从"一个人的手感"变成"团队可协作、可追溯的工程活动"的关键一步。

灰度发布

评测集跑过关,不代表可以直接全量上线。Prompt 变更同样应该走灰度发布流程,和普通功能上线的风险控制逻辑是一致的:

  1. 离线评测通过是灰度的前提,而不是终点——评测集再全面,也无法 100% 复现线上真实流量的分布。
  2. 小流量灰度:先放给一小部分真实用户或场景,同时监控线上业务指标(而不只是模型自己的评分),因为有些问题只有在真实用户的长尾输入下才会暴露。
  3. 保留快速回滚能力:新版本 Prompt 和旧版本应该可以并存、可配置切换,一旦灰度阶段发现指标异常,能立刻切回旧版本而不需要走一次完整的发布流程。
  4. 上线后持续监控、badcase 回流:即使全量上线,也要持续采样人工抽查,把新发现的问题案例重新沉淀回评测集——这样下一次 Prompt 迭代时,这些问题已经变成了"有回归保护"的已知场景,不会被重复踩坑。

把以上几节串起来,一个相对完整的 Prompt 工程化流程大致是这样:

需求 / Badcase
   ↓
起草 Prompt(角色 / 任务 / 约束 / 示例 / 输出格式)
   ↓
模板化:拆分「固定模板」与「变量」,纳入版本管理
   ↓
评测集回归测试(哪怕只改一个词)
   ↓
人工抽查显著变化的用例
   ↓
小流量灰度 + 业务指标监控
   ↓
全量上线
   ↓
持续监控 → 新 Badcase 回流评测集 → 下一轮迭代

这条链路本质上是把"写 Prompt"这件事,从一次性的创作行为,变成了一个有输入(需求/badcase)、有产出标准(评测集)、有发布纪律(灰度)、有反馈闭环(badcase 回流)的持续工程过程——这正是"把玄学变工程"这句话的具体含义。
