Prompt 基本功:角色、任务、约束、示例、输出格式

Prompt(提示词)是 AI PM 最直接的生产工具:不用写一行代码,改一改 Prompt 就能让同一个模型的产出从"能用"变成"好用"。但很多人对 Prompt 的理解还停留在"多说几句废话让它听话",结果是反复试、反复改,全靠运气——这不是工程,是玄学。

本篇讲的是"玄学"背后那套可复用的结构:一个好 Prompt 到底由哪几块组成、每一块怎么写、以及三家给行业定调的官方指南(Anthropic、OpenAI、Google)在 2026 年 7 月给出的最新共识和分歧。

好 Prompt 的解剖图

把一条写得好的 Prompt 拆开,基本都能看到这五块:

要素 回答的问题 缺失时的典型症状
角色(Role) 模型现在应该扮演谁、以什么身份说话 语气飘忽,一会儿像客服一会儿像论文
任务(Task) 具体要做什么,目标是什么 模型自由发挥,答非所问
上下文与约束(Context & Constraints) 有哪些背景信息、不能碰的边界是什么 输出脱离业务实际,或踩安全/合规红线
示例(Examples) "照这个样子做"的具体范本 格式、语气、颗粒度全靠模型猜
输出格式(Output Format) 结果应该长什么样,给谁用 拿到一段夹叙夹议的话,还得自己再解析一遍

这五块不需要每次都写满,但写 Prompt 遇到效果不稳定时,先检查这五格里哪一格是空的,往往比"重新措辞再试一次"更有效。

逐个拆解:角色、任务、约束、示例、格式

1. 角色(Role Prompting)

Anthropic 官方文档把"给 Claude 一个角色"列为通用技巧之一:在 System Prompt 里明确模型的身份、专业背景、说话方式,能让输出的专业度和语气稳定下来,而不是每次生成都在"专业顾问"和"闲聊助手"之间漂移。

  • 反例:"帮我看看这份用户反馈。"
  • 好例:"你是一名有 5 年经验的 To B SaaS 产品经理,擅长从非结构化用户反馈中识别产品机会点。请用这个身份分析以下反馈。"

角色不只是"扮演谁",更是给模型限定了知识背景和判断标准——同一份反馈,"客服"角色和"产品经理"角色会输出完全不同的分析重点。角色设定属于产品人格的一部分,更系统的做法见 系统提示词设计与 Prompt 工程化。

2. 任务(Task)

OpenAI 官方指南强调用"结果导向的语言"代替"意图导向的语言"。它给出的对比很典型:

  • 反例:"Help me with this code."(帮我看看这段代码)
  • 好例:"Review this Python function for correctness, runtime issues, and edge cases, then return a prioritized fix list."(审查这段 Python 函数的正确性、性能问题和边界情况,按优先级给出修复清单)

放到 PM 的日常场景:

  • 反例:"帮我总结一下这些用户访谈。"
  • 好例:"从这 10 份用户访谈记录里,提炼出被提及次数最多的 3 个痛点,每个痛点标注提及次数和 1 句原话引用。"

任务描述得越具体,模型需要"猜"的空间就越小。

3. 上下文与约束(Context & Constraints)

任务清楚了,还要交代清楚"在什么条件下"完成。缺失上下文是 PM 写 Prompt 最容易犯的错——脑子里想的业务背景,模型完全不知道。

约束包括:字数/篇幅限制、必须引用的信息来源、禁止出现的内容(比如不能编造数据)、语气基调、目标读者是谁。OpenAI 把"提供参考文本(reference text)"作为独立策略提出:与其让模型凭训练记忆回答,不如把权威资料直接喂给它,减少编造。这一点也是 RAG 存在的意义——检索到的材料本质上就是"喂给模型的上下文"。

4. 示例(Few-shot / Multishot Prompting)

"给例子"是三家官方指南都反复强调的技巧,但具体建议略有差异,值得放在一起看:

  • Anthropic 建议用 3-5 个高质量、有代表性的例子,并且例子要覆盖边界情况(避免模型只学到"简单模式"),用 <example> 标签把例子和指令明确分开,避免模型把例子误当成正文的一部分。
  • Google 的建议是"几乎总是应该在 Prompt 里放一些示例",但同时提醒例子不是越多越好——太多例子可能引发"过拟合"(模型死记硬背例子里的表面模式,而不是学到规律),需要在实践中试出最优数量,并保持所有示例的格式、结构完全一致。
  • OpenAI 把示例称为 few-shot learning,建议覆盖"尽可能多样的输入情况",避免模型只会处理一种输入形态。

一个 PM 场景的例子:

你是一名负责电商 App 的产品经理,需要把用户的一句话反馈,归类到以下三个标签之一:
「体验问题」「功能缺失」「价格投诉」。

<example>
输入:这个 App 打开好慢,等了快 10 秒
输出:体验问题
</example>
<example>
输入:能不能加个一键退货的功能,每次都要打客服
输出:功能缺失
</example>
<example>
输入:隔壁 App 同款便宜 20 块,你们也太黑了
输出:价格投诉
</example>

现在请分类:「客服态度还行,但是解决问题一点用没有,来回踢皮球」

这个例子里,三个 few-shot 示例分别覆盖了三个类别,格式统一(输入/输出成对出现),这正是 Anthropic 和 Google 都强调的"多样性 + 一致格式"。

5. 输出格式(Output Format)

这是最容易被忽略、但对产品化影响最大的一环。同样的分析内容,"写成一段话"和"按字段输出"的可用性天差地别——前者只能给人看,后者才能被下游代码直接消费。

OpenAI 建议用 Markdown 标题、列表或 XML 标签划出 Prompt 的功能分区(比如 Identity / Instructions / Examples / Context),这个习惯同样适用于要求模型输出结构化内容时——明确告诉模型"用几点列出""按这几个字段输出""不要输出多余解释"。当输出要被程序直接解析(比如喂给下一个系统)时,光靠"请输出 JSON"这种口头约束已经不够可靠,这正是下一篇要讲的内容:结构化输出:让模型稳定吐出 JSON。

推理模型时代,哪些老技巧要打折扣?

2024-2025 年"一步步想"(Chain of Thought,CoT)几乎是万能提效技巧;但进入推理模型(reasoning model)时代后,这条经验需要修正,三家官方指南的说法可以互相印证:

  • OpenAI 的区分很直接:推理模型(如 o 系列 / GPT-5 的推理模式)更像"资深同事"——给出目标和验收标准,让它自己规划怎么做,过度详细的步骤指导反而可能限制它自己更优的解法;而非推理的 GPT 模型更像"初级同事",需要清楚、明确、分步骤的指令才能发挥稳定。
  • Google 的官方说法更直白:Gemini 的推理模型会"自动生成内部思考过程来提升推理表现",因此通常不需要在 Prompt 里显式要求模型"列出推理步骤"或"一步步想";对特别复杂的问题,一句简单的"请深入思考后再回答"就够了,但要意识到这会增加"思考 token"的消耗和成本。
  • Anthropic 把"thinking"(扩展思考)作为独立的技巧类别单列出来,同样是模型内置的推理机制,而非纯靠 Prompt 措辞堆出来的效果。

也就是说:对开启了推理/扩展思考能力的模型,显式的"请一步步思考"逐渐从"提效技巧"变成"啰嗦甚至多余";但对不具备该能力的轻量模型(如追求低延迟的 Haiku 系产品线、GPT 非推理档位、Gemini Flash 非思考模式),CoT 依然是几乎零成本的推理增强手段。 CoT 的原理和适用场景已有专门的面试题讲解,这里不重复展开,详见:什么是 CoT(思维链)?有什么优势?。

PM 日常案例:一次完整的"差 Prompt → 好 Prompt"改写

场景:你是电商 App 的产品经理,需要模型帮你把上周的用户反馈原始记录,整理成一份可以直接发给业务方的周报摘要。

差 Prompt(五要素几乎全空)

帮我总结一下这周的用户反馈,谢谢。

问题:没有角色(不知道以什么专业视角总结)、没有约束(反馈从哪来、多长、要不要脱敏)、没有示例(不知道业务方期待什么颗粒度)、没有输出格式(可能得到一整段流水账)。结果大概率是一段泛泛而谈的话,你还得自己再加工一遍才能发出去。

好 Prompt(五要素补齐)

【角色】你是电商 App 的产品经理,正在给业务负责人写一份周度用户反馈摘要。

【任务】阅读下方本周收集到的 30 条用户反馈原始记录,提炼出本周 Top 3 高频问题。

【约束】
- 只使用给定的反馈原文,不要编造未出现的信息
- 每个问题必须标注出现次数(基于给定的 30 条数据)
- 业务负责人时间有限,总字数不超过 300 字
- 涉及具体金额、订单号等敏感信息一律脱敏为「某订单」

【示例】期待的格式参考:
<example>
1. 【物流延迟】(本周提及 12 次)用户反馈某订单发货超过承诺时效,集中在偏远地区订单。
</example>

【输出格式】
按"问题标签 + 出现次数 + 一句话概述"的结构,输出 Top 3,不要输出额外的开场白或总结语。

【本周反馈原文】
(此处粘贴 30 条原始反馈)

对比说明:同样是"总结反馈",好 Prompt 明确了输出要给谁看(业务负责人→篇幅要短)、评判标准是什么(基于原文、不编造)、长什么样子(一个具体示例)、以什么结构收尾(标签+次数+一句话)。这份 Prompt 几乎可以直接沉淀成一个可复用的模板,每周替换"反馈原文"这一个变量就能重复使用——这正是下一步"Prompt 工程化"要做的事,详见 系统提示词设计与 Prompt 工程化。
